Multi-Period Inventory Lot-Sizing

⚙ Dynamic programming — Wagner–Whitin algorithm

The business question: a distributor knows demand for the next 6 periods. Every order carries a fixed cost (PO processing, receiving, supplier minimums); every unit carried in inventory costs money to hold. Order every period and rack up fixed fees, or batch demand together and pay more to hold stock? The right answer depends on the numbers, not intuition.

This is a textbook dynamic lot-sizing problem, which has a known, provably-optimal algorithm. The original notebook applied a general-purpose continuous optimizer to what is actually a discrete, combinatorial choice — which periods to order in. That mismatch made results dependent on the solver's starting guess. Replacing it with Wagner–Whitin — a dynamic program built for exactly this problem — guarantees the true minimum-cost plan rather than "a plan that converged."

Result: with this cost structure, ordering exactly what's needed every period (just-in-time) beats any batching — holding even one period's demand one extra period costs more than a second $50 order fee. 6 orders, $300 total cost, $0 holding cost.

Sensitivity check. A real analysis tests the assumption, not just the base case. If the per-order fee rose to $400 (e.g. a supplier minimum-order surcharge), the algorithm correctly flips strategy — batching periods together because carrying extra stock is now the cheaper option:

def wagner_whitin(demand, holding_cost, order_cost):
    n = len(demand)
    cost = [[0.0] * n for _ in range(n)]
    for i in range(n):
        for j in range(i, n):
            units_carried = sum((k - i) * demand[k] for k in range(i, j + 1))
            cost[i][j] = order_cost + units_carried * holding_cost

    f = [0.0] * (n + 1)              # f[j] = min cost to cover periods 0..j-1
    order_start = [None] * (n + 1)
    for j in range(1, n + 1):
        best_cost, best_i = float("inf"), None
        for i in range(j):
            candidate = f[i] + cost[i][j - 1]
            if candidate < best_cost:
                best_cost, best_i = candidate, i
        f[j], order_start[j] = best_cost, best_i

    order_qty, j = [0] * n, n
    while j > 0:
        i = order_start[j]
        order_qty[i] = sum(demand[i:j])
        j = i
    return order_qty, f[n]

Warehouse-to-Region Transportation Optimization

⚙ Linear programming — transportation problem (scipy.optimize.linprog)

The business question: three distribution centers each have limited supply; three regions each need a certain volume. Per-unit shipping cost varies by warehouse–region pair. Which warehouse should serve which region, and how much, to minimize total freight spend while fully meeting demand and never exceeding capacity?

This is the classic transportation problem, solved exactly and efficiently with linear programming — no heuristics needed, and the solver proves the plan is cost-minimal.

Result: the optimizer concentrates volume on the cheapest lanes — e.g. Reno DC ships entirely to the East Region, its cheapest and highest-demand destination. Total freight cost: $5,830, a 12.0% reduction versus a proportional allocation (splitting each warehouse's supply across regions by demand share — a reasonable stand-in for how volume gets split without an optimization step).

Delivery Route Optimization

⚙ Combinatorial optimization — Traveling Salesman Problem (NetworkX)

The business question: a delivery truck leaves the distribution hub, visits every store exactly once, and returns — in which order should it drive to minimize total distance?

For a handful of stops, brute force can evaluate every possible route and guarantee the true optimum. That approach does not scale — route count grows factorially, so beyond roughly 10–12 stops a heuristic (nearest-neighbor + 2-opt, or a solver like OR-Tools) is the right tool instead. Stating that limit explicitly, rather than implying brute force generalizes, is part of using the technique responsibly.

Result: the optimal route (Hub → Store A → Store C → Store B → Hub) covers 80 miles, versus 95 miles for the straightforward visiting order — a 15.8% reduction. Run daily (~250 delivery runs/year), that's roughly 3,750 miles/year saved on this single route.

Methodology & Takeaways

Each case study is solved with the technique that fits its structure — not one generic solver reused three times — and every result is checked against a realistic baseline rather than reported in isolation.

Case studyTechniqueLibraryWhy this technique
Inventory lot-sizingDynamic programmingNumPyExact optimum for a discrete batching decision — no dependence on a starting guess
Warehouse allocationLinear programmingSciPy (linprog)Guaranteed-optimal, efficient at scale for balanced supply/demand networks
Delivery routingCombinatorial searchNetworkXExact for small stop counts; explicitly flagged where it stops scaling
1

Match the algorithm to the structure of the decision, not just the objective — a continuous solver was replaced with an exact dynamic program once the decision was recognized as discrete.

2

Always benchmark against a realistic baseline. "12% below proportional allocation" is a business case; "$5,830" alone is not.

3

Test sensitivity, not just the base case. The $400 order-cost what-if turns a single answer into a decision rule a procurement team can use.

4

State an algorithm's scaling limits explicitly. Brute-force routing is exact for 4 stops and unusable for 40 — worth saying, not implying otherwise.
